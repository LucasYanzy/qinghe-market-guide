# 性能、安全与工作流检查（2026-11-05）

检查基线：`f01e055`。本次修改通过 PR 提供，由仓库所有者决定是否合并和如何处理冲突。

检查覆盖公开 Pages 演示的浏览器数据库，以及 Node 应用的登录、会话和运营工作流。公开演示的角色切换仅操作当前浏览器的样例数据库；下表中的服务端登录问题适用于部署了 Node 后端的应用。

## 已复现并在本 PR 修复

| 优先级 | 问题与影响 | 复现证据 | 修复 |
| --- | --- | --- | --- |
| P1 | 切换运营场次后，若新请求失败，旧场次的商户和编辑表单仍显示在新场次下；操作可能带着旧商户、版本与表单值提交到新场次。 | 浏览器测试先加载场次 A 的商户，再让场次 B 的请求返回 503，旧代码仍保留 1 张 A 的编辑表单。 | `useWorkflow` 按请求路径绑定结果，路径变化时立即隐藏旧结果，并取消离开的读取请求。相同范围的刷新仍能保留已有数据。 |
| P2 | 未注册邮箱登录时临时生成假密码哈希，随后再次计算校验哈希。额外计算暴露账号存在性的时间线索，也放大未认证请求的 CPU 开销。 | 固定本地环境各测 12 次，已注册邮箱错误密码的中位数约 23.1 ms，未知邮箱约 46.6 ms；独立测试确认原代码分别调用 1 次与 2 次 scrypt。 | 假密码哈希在模块初始化时生成一次，每次登录统一只进行一次密码校验。错误响应保持一致。注册接口仍会明确提示重复邮箱，因此这项修复不等同于全站防账号枚举。 |
| P2 | 已登录浏览器注册新账号时，旧 cookie 对应的会话仍有效，与正常登录换号时的失效行为不一致。 | 登录 A，再携带 A 的 cookie 注册 B；原代码仍能用 A 的旧 cookie 读取 A 的登录身份。 | 登录与注册共用会话替换逻辑，成功创建新会话后删除该浏览器之前的会话。注册校验失败不会清除原登录状态。 |
| P2 | 公开演示每次 POST 都导出 SQLite 全库、编码为 base64 并同步写入 sessionStorage，即使只在计算报价或请求被校验拒绝。频繁改购物袋会重复占用主线程与临时内存。 | 5 次只读报价加 1 次格式错误的提交，原代码发生 6 次整库保存；修复后为 0 次。 | 使用 SQLite 累计变更计数跳过无数据写入的保存；真实写入仍及时保存，存储失败后允许重试。事务回滚可能增加计数，保守地多保存一次，不会因此漏存。 |
| P2 | 大屏的每秒时钟状态放在整个页面组件上，连带运营卡片和图表重新执行渲染；隐藏标签页也继续更新。 | 模拟标签页隐藏并推进 3.1 秒，原代码时钟仍变化。 | 把时钟状态放进独立组件；隐藏时清除计时器，恢复可见时立即对时并重新计时。自动刷新与手动暂停功能保留。 |

浏览器 SQLite 的单行 `get()` 同时改为读取首行后释放语句，避免先生成完整结果数组再只取第一项。

## 后续可优化项

以下项目保留为后续改进建议，未在本 PR 中改变其行为。

| 优先级 | 位置 | 当前情况与建议 |
| --- | --- | --- |
| P2 | `server/app.mjs`、`server/db.mjs` | 请求中的密码派生仍使用同步 scrypt，单次计算会阻塞 Node 主线程。本地约 23 ms 的校验时间不代表线上吞吐；可改用带并发上限的异步派生，并测试繁忙时普通请求的响应时间。 |
| P2 | `server/app.mjs` 的登录限流 | 限流按来源 IP 记录。超过 1000 条后只清理过期项，没有未过期项的硬上限；大量不同来源会增加 Map 大小和清理成本。建议添加总容量/全局限流，并验证反向代理配置。未进行公网压力测试。 |
| P2 | `src/api.ts` | 通用请求没有默认超时；单个大屏读取有单独的 15 秒超时，但其他操作可能长时间保持忙碌。建议统一超时和取消错误语义；订单写入超时必须沿用现有幂等键及结果查询，避免重复下单。 |
| P2 | `server/operations.mjs` 的取货核验 | 当前需要商户或管理员权限，并检查订单归属，但六位取货码没有单独的错误次数限制。建议按订单与操作人限速，并保留人工恢复方式。这不构成匿名买家可直接核销他人订单的证据。 |
| P3 | 公开演示首屏构建 | 主 JS 约 786 kB（gzip 250 kB），SQLite WASM 约 685 kB（gzip 336 kB）。可评估把数据库与共享业务服务移到 Worker，并按使用场景延迟初始化；需验证报价、切换角色、写入顺序和刷新恢复。当前图表及学校页面已使用独立分包，不应重复当作未拆分项。 |
